# Local Sensitive Data Encryption and Security Reassessment Results

Test date: 2026-10-31 (Asia/Kuala_Lumpur). Test scope: the local main working tree, baseline `74f6119` plus the changes under test, which were uncommitted at test time. No deployment or physical hardware was involved. The implementation and test documents were subsequently committed as `1704288` and pushed to main.

For the current encryption-deferral regression results, see [Web test results](../TEST_RESULTS.md#encryption-deferral-regression-2026-11-01).

## Overall Result

Encryption and security tests passed, along with regression checks for existing Web features. Existing data was migrated in the original isolated local database; accounts were not deleted and recreated. Names, emails, observation free text and review comments are stored as authenticated ciphertext, while authorized APIs continue to return normal text.

The initial migration covered 5 users, 251 observations and 99 reviews, containing 611 previously plaintext fields. Account IDs, password hashes, roles and relationships were preserved. New records generated by regression tests also passed the ciphertext audit. At the final audit, all 973 sensitive fields passed and the plaintext field count was 0. Counts change as fictional test records are added and do not represent real field observations.

## Security Assessment, Remediation and Reassessment

| Finding / Risk | Remediation | Verification Evidence |
| --- | --- | --- |
| Names, emails and observation/review free text were stored as plaintext | AES-256-GCM with random IVs, authentication tags and field/owning-row identity binding | Database ciphertext audit, Unicode/empty text round trips, and rejection of row/field swaps and tag tampering passed |
| Direct email lookup and uniqueness depended on plaintext | HMAC index using a separately derived key, retaining the unique constraint | Login, duplicate email rejection, registration, user management and fixture updates passed; indexes match decrypted emails |
| Incorrect keys or damaged data could trigger unsafe fallback | Strict rejection of missing/incorrect keys and non-ciphertext, with no plaintext compatibility reads | Function tests and real API fault instances passed; responses contain generic errors without data contents |
| A validly formatted but incorrect key could create mixed-key ciphertext | Database key-check marker; login and sensitive writes verify key matching first | Separate wrong-key service returned generic errors for reads and registration, without creating mixed-key users |
| Corrupted profiles must not establish authenticated sessions | Create the logged-in session only after successful authenticated profile decryption | Tampered fictional profile caused login to return 500, followed by 401 from `/auth/me.php` |
| Migration could damage IDs, passwords or business relationships | Verified encrypted snapshot before migration, transactional field updates, maintenance mode and separate operator tools | Independent temporary-database tests covered legacy schema migration, backup recovery, newer-row preservation and repeated migration |
| Web runtime account had excessive privileges | Dedicated local account with only SELECT/INSERT/UPDATE/DELETE; credentials remain private and are not displayed | `runtime_permissions.php` passed; no schema, trigger, file or administrative grants |
| Protected species deletion returned a different database error under a restricted account than root | Handle both foreign-key error codes 1217 and 1451, preserving the 409 protection response | Reproduced 500 before the fix; the same scenario and restricted-account regression passed afterwards |
| Keys/configuration could be committed or publicly accessed | Keys and encrypted snapshots outside all Git working trees; ignored `.env`; restricted Windows ACL; production checks require key and migration | Repository-path rejection, HTTP private-file protection and Git checks passed; no keys/passwords printed |

## Retention and Limitations

- Operations and recovery instructions are in `DATA_PROTECTION.md`; test scope and reproduction instructions are in `TEST_PLAN.md`.
- Keys and migration snapshots are stored in a persistent private local directory outside the repository, independent of temporary preview directories. They are not distributed through Git. Operators must maintain a separate secure key backup.
- Temporary authentication, species and device fixtures were cleaned up by the tools. The isolated database retains some fictional observations/reviews for inspection.
- This assessment does not certify full disk/database-file encryption, secure erasure of historical plaintext, production HTTPS, cloud synchronization, complete backup recovery, external penetration testing or regulatory compliance.
- The implementation, tests and documents were local and uncommitted when tested; they were subsequently published to main in commit `1704288`. Private keys, local credentials and database contents were not pushed.
